## 1. 概要

### 1.1 目的

Microsoft 365 Planner が出力するタスクリスト（CSV）を入力として、以下を行うスタンドアロンのブラウザアプリケーションである。

1. タスク間の先行・後続関係からアローダイアグラム（PERT図）を作図する
2. クリティカルパス／クリティカルチェーンを算出する
3. CCPM（クリティカルチェーンプロジェクトマネジメント）における合流バッファの挿入候補を検出する

複数の CSV ファイルを同時に読み込み、複数プロジェクトを並べて確認できる。

### 1.2 背景

Planner の無料プランには先行タスク（依存関係）を保持する機能がない。そのため、タスクの説明欄に先行タスク ID を規約に沿って記載することで依存関係を表現し、本アプリでそれを解釈してネットワーク図を構成する。

### 1.3 スコープ

**対象とする機能**

- ローカル CSV ファイルの読み込みとパース（**複数ファイル同時。1 ファイル＝1 プロジェクト**）
- 依存関係グラフの構築と妥当性検証
- **複数ファイル間のデータ不整合検出**（タスク ID の重複など。3.5.6 参照）
- 所要営業日数の算出
- アローダイアグラム（AOA 形式）への変換と描画
- 最長経路（クリティカルパス）の算出
- クリティカルチェーンの算出と合流バッファ候補の検出
- 複数プロジェクトの同時表示、および担当者の色をプロジェクト横断で一貫させること

**対象としない機能**

- Planner / Microsoft Graph API との直接連携（オフライン動作要件のため）
- タスクの編集および Planner への書き戻し
- ファイルをまたぐ依存関係の解決（3.5.2 参照）
- 複数プロジェクト間のタスク内容の比較（差分抽出）。3.5.6 のデータ不整合検出とは異なり、タスク内容の異同を比較する機能は持たない
- 進捗実績にもとづくバッファ消費率の管理（フィーバーチャート等）。**将来的に実装予定。**
- モバイル・タブレット向けレイアウト
- 複数ユーザーでの共同編集、サーバー側でのデータ保存

### 1.4 画面構成

1 画面構成。ヘッダー・メイン領域・フッターの 3 区画。**ヘッダー・フッターは 1 行に収まる高さとし、メイン領域を最大限確保する。**

| 区画 | 内容 |
| --- | --- |
| ヘッダー | アプリケーション名（固定表示。読み込んだファイル名は表示しない）と、「ファイルを開く」ボタン（複数選択可。開くたびに読み込み済みの内容に追加する）・「リセット」ボタン（メイン領域をクリアし読み込み状態を初期化する）を 1 行で配置する |
| メイン領域 | アローダイアグラム。左から右へ時間が進む向きで描画。複数プロジェクトは縦方向に積んで同時表示する（3.5.4 参照）。**ズーム操作用の拡大・縮小ボタンを設ける**（具体的な位置・デザインは **【未定】**） |
| フッター | 左端に「休日設定ファイル」ボタン（3.7 参照）・「エラー表示」ボタン（5.1 参照）・「凡例」ボタン（4.2.4 参照）をこの順で配置する。エラー表示ボタンの右側に、エラー件数を丸バッジで表示する（5.1 参照）。右端に著作権表示・ライセンス種別・サードパーティライセンスを横並びで表示（全文は表示しない。7 章参照） |

- エッジ（作業矢線）は担当者ごとに色分けする
- 配色はダークモード基調とし、純白（#FFFFFF）・純黒（#000000）は使用しない
- キーカラーは `#1414A0`（明度調整は行わず、この値をそのまま使用する）
- **主要な操作（ファイルを開く、リセット、休日設定ファイルの読み込み等）は、操作結果を画面に通知する。** 具体的な通知の表現（表示位置・形式等）は **【未定】**

### 2.1 補足事項

- **ネットワーク通信を一切行わない。** CDN からのライブラリ取得、Web フォントの読み込み、外部 API 呼び出し、テレメトリ送信のいずれも行わない。祝日情報は同梱の休日設定ファイルから取得する（3.7、4.1.1 参照）

- 配布形態や実現方式は本書の対象外とし、別途定める。
- **最低バージョンは明示的に定めず、最新版の Edge / Chrome を推奨環境とする。** Chromium 系ブラウザは自動更新が基本であり、本アプリの利用形態（個人・小規模での単一 HTML 利用）では固定バージョンへの対応要求は生じない想定のため

## 3. 入力データ

### 3.1 入力ファイル

| 項目 | 内容 |
| --- | --- |
| 形式 | CSV（Microsoft 365 Planner のエクスポート出力） |
| 取得方法 | ユーザーがファイル選択ダイアログ（複数選択可）またはドラッグ＆ドロップで指定 |
| 文字コード | **UTF-8（BOM 付き）**。サンプルで BOM（`EF BB BF`）を確認済み。BOM なしも許容する |
| 改行コード | CRLF / LF の双方を許容（サンプルは LF） |
| 区切り文字 | カンマ（`,`） |
| 引用符 | ダブルクォート（`"`）。フィールド内の改行・カンマ・エスケープされた `""` を正しく解釈すること |
| 複数ファイル | **対応する。** 1 ファイル＝1 プロジェクト（3.5 参照） |

サンプルデータ：[planner_tasks_planA_ja.csv](../test_data/planner_tasks_planA_ja.csv)、[planner_tasks_planB_ja.csv](../test_data/planner_tasks_planB_ja.csv)

### 3.2 列定義

Planner（日本語 UI）の出力列は以下の通り。

| # | 列名 | 本アプリでの用途 |
| --- | --- | --- |
| 1 | タスク ID | **必須。** ノードの一意識別子。先行タスク参照の解決キー |
| 2 | タスク名 | **必須。** 矢線ラベル |
| 3 | バケット名 | 表示・グルーピング補助のみに使用する。プロジェクト識別には使用しない（3.5 参照） |
| 4 | 進捗状況 | 表示（完了／進行中／未開始）。スタイル分岐に使用 |
| 5 | 優先度 | **使用しない** |
| 6 | 割り当て先 | **必須に準ずる。** エッジ色分けの単位。セミコロン区切りで複数指定あり。空欄あり |
| 7 | 作成者 | 未使用 |
| 8 | 作成日 | 未使用 |
| 9 | 開始日 | 所要営業日数の算出に使用。空欄あり |
| 10 | 期限日 | 所要営業日数の算出に使用。空欄あり |
| 11 | 定期的 | 対応範囲外タスクの判定に使用（3.6 参照） |
| 12 | 遅延 | **表示しない** |
| 13 | 完了日 | **使用しない** |
| 14 | 完了者 | 未使用 |
| 15 | 説明 | **必須。** 先行タスク ID の記載場所（3.3 参照）。改行を含む |
| 16 | チェックリスト アイテム | 未使用 |
| 17 | 完了したチェックリスト アイテム | 未使用 |
| 18 | ラベル | **使用しない** |

Planner の UI 言語によって列名（ヘッダー行）は変わるが、**英語ロケール出力への対応は行わない。** 日本語 UI の出力のみを対象とする。

### 3.3 先行タスクの記法

説明欄に以下の形式で先行タスク ID を記載する。

```
先行タスク:sETiMVQJxjszVcn27Dhpjf3Y-uAA,hzjGjjr_kZX2jL91bEj9AqhGjTAA
```

| 項目 | 規約 |
| --- | --- |
| キーワード | `先行タスク:` |
| 大文字小文字 | 抽出処理はアルファベットの大文字小文字を区別しない（キーワード自体は日本語のため実質的に影響しない） |
| 区切り | カンマ（`,`） |
| 空白 | ID 前後の空白は許容し、トリムする |
| 出現位置 | 説明欄の任意の行。**サンプルでは説明欄の 1 行目**に記載され、2 行目以降が本来の説明文となっている |
| 出現回数 | 1 タスクにつき 1 回。**複数回出現した場合はエラーとする**（E204、5.2.2 参照） |
| 記載なし | 先行タスクなし（開始タスク）とみなす |
| 説明文の扱い | `先行タスク:` の抽出にのみ説明欄を参照する。**残りの説明文は画面に表示しない** |

サンプルにおける実際の記載例（説明欄全体がダブルクォートで囲まれ、改行を含む）:

```
"先行タスク:sETiMVQJxjszVcn27Dhpjf3Y-uAA,hzjGjjr_kZX2jL91bEj9AqhGjTAA
As-Is / To-Be の業務フローを図式化する。"
```

> サンプルデータには `先行タスク:` を持たないタスクも 8 件含まれる（週次進捗ミーティング、ログ出力方針の統一 等）。これらは先行・後続を持たない孤立タスクとなる（3.6 参照）。

### 3.4 データ形式の詳細

| 項目 | 仕様 |
| --- | --- |
| タスク ID | 英数字・`-`・`_` からなる文字列（サンプルでは 28 文字） |
| 日付 | **`YYYY/MM/DD` 形式のみを許容する。** 他形式は不正な日付として扱う（W307 参照） |
| 複数値 | 割り当て先・ラベル・チェックリストはセミコロン（`;`）区切り |
| 空欄 | 開始日・期限日・割り当て先に空欄が存在する（サンプル 17・43 行目等） |
| 改行入りフィールド | 説明欄に改行を含む行が存在する（サンプル 44〜46 行目）。ダブルクォートで囲まれる |
| 引用符入りフィールド | 説明欄に `""` によるエスケープを含む行が存在する（サンプル 47 行目） |

### 3.5 複数ファイルの読み込みとプロジェクト識別

Planner の出力にプロジェクトを識別する列は存在しない（バケット名は工程名であり、プロジェクト単位ではない）。本アプリでは **CSV ファイル 1 つを 1 プロジェクトとして扱う。**

| 項目 | 仕様 |
| --- | --- |
| 読み込み単位 | 1 CSV ファイル ＝ 1 プロジェクト |
| 読み込み操作 | ヘッダーの「ファイルを開く」ボタン（複数選択可）、または複数ファイルのドラッグ＆ドロップ。同じ操作で追加読み込みもできる |
| 処理順序 | 一度に複数ファイルを選択した場合も、**ファイル名の昇順で 1 ファイルずつ逐次検証する**（選択ダイアログの選択順はブラウザ・OS 依存で不定のため用いない）。1 ファイルずつ繰り返し読み込んだ場合と結果は一致する |
| 上限超過・重複時の扱い | ファイル数（E402、上限 **20 個**）・合計タスク件数（E401、上限 **10,000 件**）・同名ファイル（E205）・同一タスク ID（E206）のいずれかに該当する場合、**ファイル名昇順で該当ファイルのみを個別に拒否する。** 既存の読み込み済みプロジェクトの状態は変更しない（5.2.2, 5.2.5 参照） |
| 反映のタイミング | 検証に成功したファイルから順に、その場でプロジェクトとして追加する。一部が失敗しても、それ以前に成功した分は取り消さない |
| 全解除 | 個別解除は行わない。ヘッダーの「リセット」ボタンで読み込み済みの全プロジェクトを一括解除する |
| プロジェクト名 | 内部的にはファイル名（拡張子を除く）をプロジェクトの識別・エラー表示に用いる。**画面上には表示しない**（3.5.4 参照） |
| 表示順（レーンの並び） | **各プロジェクトの基準日（4.1.5 参照）順に自動で並べる**（読み込み順ではない）。手動での並べ替えは行わない |

#### 3.5.1 タスク ID のスコープ

**タスク ID はファイル単位のスコープとする。** タスク ID 単体をプロジェクトをまたぐ識別キーとして扱ってはならない（内部でのキー構成方法は本書の対象外とし、別途定める）。これは実装を、想定外の入力（複数ファイルの取り違え等）に対して脆くしないための保険であり、**ファイル間でのタスク ID の重複を許容する趣旨ではない。** 3.5.6 のデータ不整合検出により、複数ファイルに同一のタスク ID が出現した場合はエラー（E206）として読み込みを拒否する（5.2.2 参照）。

> サンプルデータ [planner_tasks_planA_ja.csv](../test_data/planner_tasks_planA_ja.csv) と [planner_tasks_planB_ja.csv](../test_data/planner_tasks_planB_ja.csv) は、タスクの前後関係（依存構造）は同一のまま、タスク ID をそれぞれ独立させた別プロジェクトのデータである。両方を読み込んでも E206 は発生しない。

#### 3.5.2 ファイルをまたぐ依存関係

**対応しない。** `先行タスク` の参照は、同一ファイル内のタスクに対してのみ解決する。他ファイルに同一の ID が存在する場合、それは依存関係の参照対象としてではなく、**3.5.6 のデータ不整合として明確にエラーとする**（E206）。他ファイルの ID を暗黙に参照できてしまう状態は許容しない。

**【未定】** 将来ファイル間依存を扱う場合、`先行タスク:<プロジェクト名>::<タスクID>` のような修飾記法が必要となる。3.5.1 の通りファイル間でのタスク ID の重複はエラーとして排除されるため、無修飾の ID でも一意に参照先を特定できる。ただし、現時点ではファイル間の依存関係解決自体を要件に含めない。

#### 3.5.3 プロジェクト横断で共有する情報

| 情報 | 扱い |
| --- | --- |
| 担当者と色 | **全プロジェクト横断で同一人物には同一色を割り当てる。** 氏名文字列の完全一致で同定する。**表記ゆれ（全角半角スペース等）の正規化は行わない** |
| 時間軸 | 営業日数の算出には全プロジェクト共通の非営業日カレンダー（休日設定ファイル、3.7・4.1.1 参照）を用いる。表示上の横軸位置は、共通の原点（グローバル営業日番号）に揃える（4.1.5 参照） |
| リソース競合 | **全プロジェクトを横断して担当者の競合を判定する**（4.1.3 参照） |

#### 3.5.4 複数プロジェクトの表示

**縦方向に積んで同時表示する（スイムレーン形式）に確定。** 横軸（時間）は全プロジェクトで揃える（4.2.4 参照）。**プロジェクト名は画面上に表示しない。**

**【要調整】** レーンの高さ、プロジェクト間の余白、レーン間の境界の具体的表現（4.2.4 のプロジェクト境界の表現と同一論点）などの詳細は仕様として確定させず、画面モックアップを作成しながら別途調整する。

#### 3.5.5 孤立タスクの扱い

依存関係を持たないタスク（先行も後続もない）は、**そのファイル内の他タスク（依存関係を持つグループ）とは別に、独立したプロジェクト（レーン）として扱う。** 1 ファイル内に孤立タスクが複数存在する場合は、それらをまとめて 1 つの独立プロジェクトとする。サンプルには週次進捗ミーティング・要員計画の見直し等、8 件の孤立タスクが含まれる。

> この独立プロジェクトの表示順（3.5 参照）も、基準日（4.1.5 参照）に基づいて決定する。

#### 3.5.6 複数ファイル間のデータ不整合検出

複数ファイルを比較する機能を持つが、**その目的はタスク内容の異同比較ではなく、意図しないデータ不整合（コピー＆ペースト等の作業ミス）の検出に限定する。**（1.3 参照）

| 検出内容 | 扱い |
| --- | --- |
| 同一のタスク ID が複数ファイルに出現する | **エラーとする**（E206、5.2.2 参照）。該当ファイル名とタスク ID を表示し、後から読み込もうとしたファイルの追加を拒否する |

> 内容が完全に同一のファイルを誤って複数回読み込んだ場合（ファイル名のみが異なる等）も、全タスクの ID が重複するため、この E206 によって検出・拒否される。この場合専用の別警告は設けない。

### 3.6 特殊なタスクの扱い

| 対象 | 論点 |
| --- | --- |
| 定期的＝はい のタスク | **対応範囲外。** 週次会議等、繰り返しタスクはネットワーク図の対象としない。読み込んだファイルに含まれていた場合は、可能な限りエラーとせず、ネットワークから除外して処理を継続する（警告 W312、5.2.3 参照）。**除外したタスクの ID を先行タスクとして参照していた辺は、参照先が存在しない場合（W301）と同様に無視する。** 後続タスク自体は除外しない |
| 開始日・期限日が空のタスク | **所要日数を 3 営業日として仮置きする。** 当該タスクのエッジは、通常の直線・折れ線ではなく**ジグザグの実線**で描画し、値が仮置きであることを示す（W304/W305、5.2.3 参照） |
| 進捗状況＝完了 のタスク | **実績（開始日・期限日欄の値）で固定する。** CSV に記載された開始日・期限日をそのまま用いて所要日数を算出し、特別な調整は行わない |
| 割り当て先が空のタスク | エッジ色の割り当て。「未アサイン」用の色を用意する |
| 複数担当のタスク | **担当者ごとに実作業のエッジを作成する。** 元のタスクの開始・終了イベントに加えてノードを追加し、各担当者のエッジを 0 営業日のダミー矢線で元のイベントに接続する（4.2.3 参照）。所要日数はどの担当者のエッジも元のタスクと同じ値とする。リソース競合判定は担当者ごとに生成されたエッジを単位として行う |

### 3.7 休日・祝日設定ファイル

営業日数の算出（4.1.1 参照）で用いる非営業日を定義するファイル。**外部 API との通信は行わず、ファイルの読み込みのみで完結させる**（完全オフライン要件、2 章参照）。

| 項目 | 内容 |
| --- | --- |
| 形式 | CSV。ヘッダー行なし。1 行 1 件、`日付,名称` の 2 列 |
| 日付形式 | `YYYY-MM-DD`（ハイフン区切り）。**タスク CSV の日付形式（`YYYY/MM/DD`、3.4 参照）とは異なる点に注意** |
| 名称列 | 祝日名、または「土曜」「日曜」等のラベル。**使用しない。** 日付列のみを読み込みの対象とする |
| 既定ファイル | [japan_holidays_2025FY-2027FY.csv](../data/japan_holidays_2025FY-2027FY.csv)。日本の祝日・振替休日・国民の休日と、土曜・日曜をあらかじめ列挙したもの。対象期間は 2025 年度〜2027 年度（2025-04-05 〜 2028-03-20） |
| 読み込み方式 | アプリに同梱され、起動時に自動で読み込まれる。**単一 HTML 配布かつ `file://` での動作を前提とするため（2 章参照）、既定ファイルの内容はビルド時に HTML 内へ埋め込む。実行時に外部ファイルとして動的に読み込むことはしない**（実現方法は本書の対象外とし、別途定める）。加えて、**同一フォーマットのファイルを利用者が読み込めるようにする**（対象期間の拡張・差し替え用）。フッター左端の「休日設定ファイル」ボタンから行う（1.4 参照） |
| 読み込み時の扱い | **置き換える。** 利用者がファイルを読み込むと、既定ファイル（またはそれ以前に読み込んだファイル）の内容を破棄し、新しく読み込んだファイルの内容のみを用いる |
| 既読プロジェクトへの反映 | 休日設定ファイルを置き換えた時点で、**読み込み済みの全プロジェクトについて、所要日数・クリティカルパス／クリティカルチェーン・合流バッファ候補・図の描画を即座に再計算する。** ファイルの再読み込みは不要 |
| 対象期間外の日付 | ファイルに記載のない日付は祝日として考慮しない。**ただし土曜・日曜は、ファイル（埋め込まれた既定ファイルを含む）の対象期間・記載有無によらず、4.1.1 の規則により日付から機械的に算出し、常に非営業日として判定する（外挿する）。** 既定ファイルの対象期間（2025 年度〜2027 年度）を超える日付についても同様である |
| 不正な行の扱い | 日付形式が不正な行は、その行のみを無視して読み込みを継続する（W313、5.2.3 参照） |

## 4. 処理ロジック

### 4.1 全体ロジック

処理は以下のパイプラインで構成する。**ステージ [1]（ファイル読み込み）は `FileReader` による I/O、ステージ [13]〜[14]（集約・レイアウト・描画）は画面への反映を伴う副作用層である。ステージ [2]〜[12]（CSV パース以降、AOA 変換・時刻計算・クリティカルパス／バッファ算出まで）は、副作用を持たない純粋関数群として実装し、単体テストの対象とする。**

ステージ [1]〜[12] は **CSV ファイル 1 つにつき 1 回、独立して実行する。** ファイル間で状態を共有しないため、1 つのファイルで致命的エラーが発生しても、他のファイルの処理は継続できる。

**ステージ [0] は、選択ファイル数・各ファイルのサイズのみを用いる事前検証であり、ファイル内容の読み込みより前に実行する。** 巨大なファイルでも、内容をメモリに読み込む前に上限超過を検出できる（拒否の粒度は 3.5 の方針に従う。具体的な検証手段は別途定める）。

```
[0] 事前検証（ファイルのメタデータのみ、内容は読まない、ファイル名昇順で判定）
      ↓  読み込み済み件数が上限（20 個）に達した以降のファイルを拒否（E402）
      ↓  各ファイルのサイズが上限（10MB）を超えるファイルを拒否（E404）
  ファイルごとに繰り返し ─────────────────────────────┐
                                                      │
[1] CSV 読み込み（FileReader）                        │
      ↓  生テキスト                                   │
[2] CSV パース                   → レコード配列       │
      ↓                                               │
[3] タスクモデルへの正規化        → Task[]            │
      ↓   （ID・名称・担当者・開始日・期限日・説明）  │
[4] 先行タスク抽出（先行タスク:）→ 依存辺 Edge[]      │
      ↓   （参照解決は同一ファイル内に限定）          │
[5] 妥当性検証                    → エラー／警告      │
      ↓                                               │
[6] タスクグラフ構築（AON）       → 有向グラフ G      │
      ↓                                               │
[7] 所要営業日数の算出            → duration          │
      ↓                                               │
[8] 孤立タスクの分離              → 独立プロジェクト  │
      ↓                          として扱う（3.5.5）  │
[9] アローダイアグラム変換（AOA） → イベント・矢線    │
      ↓                          （4.2）              │
[10] 時刻計算                     → ES/EF/LS/LF/TF    │
      ↓                                               │
[11] クリティカルパス／チェーン算出                   │
      ↓                                               │
[12] 合流バッファ候補の検出                           │
                                                      │
  ─────────────────────────────────────────────────┘
      ↓  Project[]（プロジェクト単位の結果）
[13] 全プロジェクト横断の集約
      ↓   ・担当者と色の対応表の生成（3.5.3）
      ↓   ・共通時間軸（グローバル原点）の算出（4.1.5）
      ↓
[14] レイアウトと描画
```

#### 4.1.1 所要営業日数の算出（ステージ 7）

| 項目 | 仕様 |
| --- | --- |
| 定義 | 開始日から期限日までの営業日数 |
| 両端の扱い | 開始日・期限日の両方を含む（inclusive）。例：4/6(月)〜4/10(金) → 5 営業日 |
| 非営業日 | 土曜・日曜を除外する |
| 祝日 | **考慮する。** 休日設定ファイル（3.7 参照）に列挙された日付を非営業日として扱う。既定は [japan_holidays_2025FY-2027FY.csv](../data/japan_holidays_2025FY-2027FY.csv) |
| 日付欠落時 | **所要営業日数を 3 日として仮置きする**（3.6、W304/W305 参照） |
| 開始日 > 期限日 | 開始日・期限日が空のタスクと同様、所要日数を 3 営業日として仮置きする（W306、5.2.3 参照）。エラーとはしない |

#### 4.1.2 時刻計算（ステージ 10）

有向非巡回グラフ上の動的計画法で算出する。

- **前進計算**：トポロジカル順に最早結合点時刻 `ES(j) = max(ES(i) + d(i,j))` を求める（プロジェクト開始イベントの `ES = 0`）
- **後進計算**：逆トポロジカル順に最遅結合点時刻 `LS(i) = min(LS(j) - d(i,j))` を求める
- **トータルフロート**：`TF(i,j) = LS(j) - ES(i) - d(i,j)`
- ダミー矢線の所要日数は 0
- 単位は営業日
- **ここで求める ES/LS は、あくまでプロジェクト単体を 0 起点とした相対値である。** CSV の開始日・期限日は、4.1.1 の所要日数（`duration`）の算出にのみ使用し、この時刻計算そのものには使用しない。複数プロジェクトを横断した表示上の位置（横軸）は、この相対値に 4.1.5 のオフセットを加えて求める

#### 4.1.3 クリティカルパスとクリティカルチェーン（ステージ 11）

| 項目 | 仕様 |
| --- | --- |
| クリティカルパス | `TF = 0` の作業矢線がプロジェクト開始イベントから終了イベントまで連なる経路。最長経路と一致する |
| 複数経路 | 同長のクリティカルパスが複数存在しうる。**全件を保持し、すべて強調表示する。** どちらを重視するかを利用者が判断できるよう、選択肢として提示する |
| クリティカルチェーン | 本来はリソース（担当者）の競合を解消したうえでの最長連鎖を指すが、**本アプリではリソースレベリング（並行作業の直列化）は行わず、クリティカルパスと同一のものとして算出する** |

> **クリティカルチェーンの算出方式は、リソース競合を考慮しないことに確定した。** クリティカルパス＝クリティカルチェーンとして扱う。同一担当者に割り当てられた並行作業の直列化（リソースレベリング）は行わない。
>
> なお、3.5.3 のリソース競合検出（全プロジェクト横断で担当者の掛け持ちを検出する機能）は、この算出方式とは独立した情報提供機能として維持する。検出結果をクリティカルチェーンの算出には反映しない。

#### 4.1.4 合流バッファ候補の検出（ステージ 12）

**検出条件**：クリティカルチェーン上のイベントのうち、以下を満たすもの。

1. 入次数が 2 以上である
2. 入辺のうち少なくとも 1 本がクリティカルチェーンに属さない（＝フィーディングパスからの合流）

**出力**：合流イベント、合流元のフィーディングパス、そのパスの長さ、フロート量。

**バッファサイズの算出は将来実装予定とする。** 第 1 版では合流バッファ候補の検出（発生位置の提示）のみを行い、サイズ算出方式（1/2 法、SSQ 等）は実装しない。

**プロジェクトバッファ（クリティカルチェーン末尾のバッファ）の算出・表示も将来実装予定とする。**

#### 4.1.5 共通時間軸への変換（ステージ 13）

4.1.2 の ES/LS は、プロジェクトごとに開始イベントを 0 とする**相対的な営業日番号**である。この変換は、**依存関係と所要日数から算出したネットワーク計画を、各プロジェクトの実際の開始日を起点として配置し直す表示上の処理**である。**この変換は表示（4.2.4）にのみ適用し、ES/LS・クリティカルパス・合流バッファ候補の算出結果自体は変更しない。**

> **注記：** この配置はプロジェクトの起点を実際の暦日に合わせるものであり、個々のタスクの CSV 記載の開始日を横軸上に個別再現するものではない。後続タスクの位置は計算上の ES に従うため、実際の開始日とずれる場合がある。

| 項目 | 仕様 |
| --- | --- |
| プロジェクトの基準日 | そのプロジェクトの先行タスクを持たないタスク（開始イベントの直後のタスク）のうち、**有効な（欠落していない）CSV 記載の開始日を持つものの中で最も早い実際の日付** |
| 基準日が決められない場合 | 先行タスクを持たないタスクの開始日がすべて欠落している場合、**そのプロジェクトに含まれる全タスクの中で、有効な開始日を持つものの中で最も早い日付**を代わりに用いる。それでも 1 件も存在しない場合（＝そのプロジェクトに有効な開始日が 1 件もない）は、警告（W315）を表示し、**そのプロジェクトのオフセットを 0 とする**（全体の原点上に配置する） |
| 全体の原点（グローバル営業日番号 0） | 読み込み済みの全プロジェクト（3.5.5 の孤立タスクによる独立プロジェクトを含む）のうち、**有効な基準日を持つプロジェクトの基準日の中で最も早いもの。** その日付が非営業日（土日・祝日）の場合は、直後の最初の営業日を原点とする |
| 全プロジェクトに有効な基準日が 1 件もない場合 | 実日付に基づく原点を定義できないため、**実日付と結び付かない仮想的な営業日番号 0 を原点とする。** この場合、すべてのプロジェクトのオフセットは 0 になる |
| プロジェクトのオフセット | 各プロジェクトの基準日を、休日設定ファイル（3.7 参照）に基づく共通の非営業日カレンダーで、全体の原点からの営業日数に変換した値。基準日が非営業日の場合は、直後の最初の営業日で換算する |
| 表示上の横軸位置 | タスクの ES（4.1.2、プロジェクト内相対値）＋ 所属プロジェクトのオフセット |
| 孤立タスクの独立プロジェクト（3.5.5）の基準日 | 上記と同じ規則を適用する。含まれる孤立タスクの開始日がすべて欠落している場合も同様に W315 とする |

読み込み済みプロジェクトの追加・解除により全体の原点は変動しうるため、その都度再計算する（4.2.4 の配色パレット再生成と同様の性質を持つ）。

### 4.2 アローダイアグラムパーサー

タスクと依存関係の集合（AON：Activity on Node）を、アローダイアグラム（AOA：Activity on Arrow）へ変換するモジュール。作図ルールはアローダイアグラムの標準的な規約に従う。

#### 4.2.1 用語と作図ルール

| 用語 | 定義 |
| --- | --- |
| イベント（結合点） | 円で表す節点。作業の開始・完了の時点を表し、それ自体は時間を消費しない |
| 実作業 | 実線の矢線。1 本が 1 タスクに対応し、所要営業日数を持つ |
| ダミー作業 | 破線の矢線。所要日数 0。依存関係のみを表現する |

**遵守する作図ルール**

1. 矢線は左から右へ向かう。逆走・ループを作らない
2. 開始イベントは 1 つ、終了イベントは 1 つ（プロジェクト単位）
3. イベント番号は矢線 `(i, j)` について常に `i < j` となるよう付番する
4. 同一のイベント対 `(i, j)` を結ぶ実作業は 1 本のみとする（並行作業はダミーで分離する）
5. 依存関係を過不足なく表現する。実在しない依存を生じさせない

#### 4.2.2 入出力

本モジュールは**プロジェクト（＝1 ファイル）単位で呼び出す。** 複数プロジェクトを 1 つのアローダイアグラムに統合することはない。

タスクと依存関係の集合（所要日数を含む）を入力とし、アローダイアグラムを構成するイベントと矢線の集合を出力する。タスク ID は当該プロジェクト内でのみ一意であればよい（3.5.1）。具体的なデータ構造は本書の対象外とし、別途定める。

#### 4.2.3 変換アルゴリズム

AON（タスクと依存関係）から AOA（イベントと矢線）への具体的な変換手順、およびダミー矢線の削減方法は本書の対象外とし、別途定める。手順は 4.2.1 の作図ルールをすべて満たすことを設計上の制約とする。

**推移的冗長辺（A→B、B→C、A→C の A→C）の除去は将来実装予定とする。** 第 1 版では除去せず、利用者が明示的に記載した依存はすべて描画する。

#### 4.2.4 レイアウト

座標計算方式（時間軸との対応、交差最小化のアルゴリズム等）は本書の対象外とする。ここでは表示上の要件のみを定める。

| 項目 | 仕様 |
| --- | --- |
| 矢線の描画 | **折れ線。** ただし所要日数が仮置き（3.6 参照）のタスクは**ジグザグの実線**とする |
| 色分け | 実作業の矢線を担当者ごとに色分けする。**色の割り当ては全プロジェクト横断で一貫させる**（3.5.3）。**固定のパレットは持たず、読み込み済みの全プロジェクトの担当者数に応じて色相環（Hue）を均等分割し、都度動的に生成する。** ファイルの追加・解除で担当者数が変わるたびに再生成される。**色と担当者名の対応は凡例パネルで確認できる**（下記参照） |
| プロジェクト境界 | 複数プロジェクト表示時、**各プロジェクトの領域をグレーの水平線で区切る**（プロジェクト名は表示しない。3.5.4 参照） |
| ダミー | 破線・無彩色 |
| クリティカルチェーン | **強調表示は矢線（エッジ）のサイズを大型化することで表現する**（線幅を太くする） |
| 合流バッファ候補 | **強調表示は合流イベント（ノード）のサイズを大型化することで表現する** |
| 操作 | **ズーム・パンに対応する（Google マップの UI と同様のマウスホイール操作・ドラッグ操作）。タスク詳細のツールチップ表示は行わない** |
| プロジェクトを縦積み表示（3.5.4 案 A）する場合の時間軸 | 横軸は**グローバル営業日番号**（4.1.5 参照）とする。カレンダー日付そのものへの変換は行わない |

**凡例パネル：** 担当者ごとの色分けが、どの担当者を指すか確認できるよう、凡例を設ける。

- フッター左端の「凡例」ボタン（1.4 参照）で開閉する。パネルは通常は折りたたまれている
- 展開すると、**担当者名と、その担当者に割り当てられた色の組み合わせを一覧表示する**（「未アサイン」用の色を含む。3.6 参照）
- 色相環による動的な色再生成（上記「色分け」参照）が発生するたびに、凡例の内容も追従して更新される

## 5. エラー処理

### 5.1 方針

- エラーは **致命的エラー** と **警告** に区分する
- **エラーの影響範囲はファイル単位に閉じる。** あるファイルで致命的エラーが発生しても、他のファイルの読み込みと描画は継続する。エラーとなったファイルのみ読み込み対象から除外し、その旨を表示する
- 致命的エラーは、原因と該当箇所（**ファイル名**・行番号・タスク ID）を画面に表示する
- 警告は処理を継続し、該当タスクを図上で識別可能にしたうえで一覧表示する
- オフライン動作要件のため、エラー情報の外部送信は行わない
- **致命的エラーが単発（1 件）の場合は `alert` で表示する。**
- **複数件、または複数ファイルにまたがる場合は、専用のエラー表示パネルに一覧表示する。** パネルは通常は折りたたまれており、フッター左端の「エラー表示」ボタン（1.4 参照）で展開する。折りたたまれている間も、**ボタン右側に丸バッジでエラー件数を表示する**（エラーが 0 件の場合はバッジを表示しない）
- **パネルの形式：** テキストが縦に連なり、スクロールできる一覧とする。エラー 1 件につき以下の行で構成する。
  - 1 行目：`<ファイル名> - <ステージ名>`（例：`planB.csv - データ整合性`）
  - 2 行目以降：エラーコード・メッセージ等、エラーの内容を 1 行ずつ列挙する
- **ステージ名は、5.2 のエラー分類に対応させる。** `E1xx`＝「ファイル・パース」、`E2xx`＝「データ整合性」、`E4xx`＝「処理」

### 5.2 エラー一覧

#### 5.2.1 ファイル・パース系（致命的）

| ID | 事象 | メッセージの要点 |
| --- | --- | --- |
| E101 | ファイルが CSV として解釈できない | 形式不正 |
| E102 | ヘッダー行が存在しない | 先頭行を確認 |
| E103 | 必須列（タスク ID／タスク名／説明）が存在しない | 欠落している列名 |
| E104 | 文字コードを判別できない／文字化けしている | UTF-8 での再出力を案内 |
| E105 | データ行が 0 件 | 内容が空 |

#### 5.2.2 データ整合性系（致命的）

| ID | 事象 | 対応 |
| --- | --- | --- |
| E201 | **同一ファイル内で**タスク ID が重複している | 該当 ID を表示して当該ファイルを中止。ファイルをまたぐ ID の重複は E206 として別途検出する（3.5.1, 3.5.6） |

## 6. セキュリティ設計

### 6.1 方針

CSV から読み込む文字列（タスク名、担当者名、ファイル名、タスク ID 等）は、外部から与えられる**信頼できない入力**として扱う。これらは画面（矢線ラベル、凡例パネル、エラーメッセージ等）に表示されるため、XSS（クロスサイトスクリプティング）等のリスクに対して**多層防御**を行う。**いずれか一層が破られても被害が拡大しないよう**、独立した複数の防御層を設ける。説明文は画面に表示しない（3.3 参照）ため対象外とする。

### 6.2 防御層

| 層 | 目的 | 概要 |
| --- | --- | --- |
| 入力の無害化 | CSV 由来の文字列が HTML／SVG として解釈される余地をなくす | CSV 由来の文字列は常にテキストとして扱い、HTML／属性の構文として解釈されうる形では出力しない。具体的な実装手段（使用する DOM API、属性値の制限方法等）は本書の対象外とし、別途定める |
| リンク化の禁止 | 外部への遷移経路そのものを作らない | CSV 由来の文字列（タスク名等）はリンク化せず、**常にプレーンテキストとして表示する。** リンク（`<a>` 要素）を生成する機能は持たない |
| イベントハンドラの統一 | HTML 属性経由でのスクリプト実行を防ぐ | スクリプトの実行は JavaScript による動的なイベント登録に限定し、HTML のインラインイベント属性（`onclick` 等）は使用しない。これは CSP（後述）が正しく機能するための前提でもある |
| CSP（Content Security Policy） | 万一上記が回避されても、注入されたスクリプトを実行させない。実行された場合でも外部への情報送信を防ぐ | `default-src 'none'` を土台とする。`script-src` は `'unsafe-inline'` を使用せず、ビルド後の実際のインラインスクリプトのハッシュ値（`'sha256-...'`）のみを許可する（6.3 参照）。`style-src` は `'unsafe-inline'` を許可する。`connect-src` は許可せず、完全オフライン要件（2 章参照）を裏付ける |

これらは独立した層であり、いずれか 1 つが突破されても、他の層が被害の拡大（任意コード実行、外部への情報送信等）を防ぐことを意図する。実装上の具体的な手段・理由づけは本書の対象外とし、別途定める。

### 6.3 CSP の位置づけ

配布形態が HTML ファイル単体となる場合、CSP は HTTP レスポンスヘッダーではなく `<meta>` タグで指定する必要がある。**`<meta>` タグによる配信では `frame-ancestors` ディレクティブは効力を持たず、他サイトへの埋め込み（クリックジャッキング等）の防止は保証できない。** これを保証する必要がある場合は、HTTP レスポンスヘッダーを設定可能な配布形態への変更が必要になるが、その判断は本書の対象外とする。

**また、CSP の `<meta>` タグは許可対象のインラインスクリプトよりも必ず前に出力しなければならない。** `<meta>` による CSP は、そのタグより前に解析・実行された要素には遡って適用されないためである（具体的な配置方法は別途定める）。

CSP は他の防御層が突破された場合の**最終防御線**であり、外部への不正な情報送信（データの持ち出し）を防ぐことを主目的とする。完全オフライン動作要件（2 章参照）とも整合する。

**ディレクティブ全文は以下の通り確定する。**（`script-src` のハッシュ値は例。実際の値はビルドごとに算出する）

```
default-src 'none';
script-src 'sha256-<ビルド時に算出したインラインスクリプトのハッシュ値>';
style-src 'unsafe-inline';
connect-src 'none';
font-src 'none';
frame-src 'none';
object-src 'none';
media-src 'none';
img-src 'none';
base-uri 'none';
form-action 'none';
frame-ancestors 'none';
```

| ディレクティブ | 値 | 根拠 |
| --- | --- | --- |
| `default-src` | `'none'` | 明示的に許可した以外はすべて拒否する土台 |
| `script-src` | `'sha256-...'`（ビルド時算出） | 単一 HTML への全インライン展開のため許可が必要だが、`'unsafe-inline'` は注入されたスクリプトも実行してしまうため使用しない。ビルド後の正規スクリプトのハッシュ値のみを許可する（6.2「イベントハンドラの統一」が前提） |
| `style-src` | `'unsafe-inline'` | 単一 HTML への全インライン展開のため必須。CSS 注入は `img-src`／`connect-src` の `'none'` により外部への持ち出し経路が塞がれているため、スクリプトほど厳格なハッシュ化は行わない |
| `connect-src` | `'none'` | 完全オフライン要件（2 章参照）。外部通信を一切行わない |
| `font-src` | `'none'` | OS 標準フォントのみを使用し、Web フォントを読み込まない（2.1 参照） |
| `frame-src` | `'none'` | iframe 等の埋め込みコンテンツを使用しない（1 画面構成、1.4 参照） |
| `object-src` / `media-src` | `'none'` | プラグイン・音声・動画を使用しない |
| `img-src` | `'none'` | ファビコン等の画像を一切使用しない |
| `base-uri` | `'none'` | `<base>` タグによる相対 URL 基点の書き換えを禁止する |
| `form-action` | `'none'` | フォーム送信を行わない（ファイル読み込みは `<input type="file">` と JavaScript のみで完結する） |
| `frame-ancestors` | `'none'` | **`<meta>` 配信では効力を持たない。** 埋め込み防止は保証されないことを踏まえたうえで、意図を示す宣言として記述する |

### 6.4 データの取り扱い

- CSV に由来するデータ（タスク内容、ファイル名等）は、`localStorage`・`IndexedDB`・URL（クエリパラメータ等）・コンソールログのいずれにも保存・出力しない
- 「リセット」操作（1.4 参照）を行った際は、メモリ上に保持しているプロジェクトデータ・エラー詳細、および生成済みの Blob URL（存在する場合）をすべて破棄する
