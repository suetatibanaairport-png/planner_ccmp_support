## 1. 配布形態

完全オフライン動作の要件（機能仕様書 2 章）を満たすため、**単一 HTML ファイル**として配布する。利用者はファイルをダブルクリックしてブラウザで開くだけで使用できる。

> **`file://` スキームでの制約（重要）**
> `file://` で開いた HTML では、ES モジュール（`<script type="module">`）と `fetch` が CORS ポリシーによりブロックされる。したがって、
> - すべての JavaScript / CSS を 1 つの HTML にインライン展開する
> - 外部ファイルの動的読み込みを行わない
> - CSV の読み込みは `<input type="file" multiple>` と `FileReader` API を用いる（これは `file://` でも動作する）。複数ファイルのドラッグ＆ドロップも `DataTransfer.files` で取得できる
>
> ことが必須となる。

**事前検証（機能仕様書 4.1 ステージ [0]、E402/E404）は、`FileReader` による内容読み込みより前に、`FileList.length`（選択ファイル数）と各 `File` オブジェクトの `size` プロパティ（ファイルサイズ）のみを用いて行う。** これらはファイル内容にアクセスせず同期的に取得できるため、上限超過時に内容を一切メモリに読み込まずに中止できる。

**既定の休日設定ファイル（機能仕様書 3.7）にも同様の制約が適用される。** `japan_holidays_2025FY-2027FY.csv` を実行時に `fetch` 等で外部ファイルとして読み込むことはできないため、**ビルド時にファイルの内容を JavaScript の文字列リテラルとして読み込み、バンドルする HTML 内に埋め込む。** 起動時はこの埋め込み文字列を、アップロードされた休日設定ファイルと同一の CSV パーサー（3.7 参照）で解釈し、パース処理を分岐させない。

**配布形態は単一 HTML ファイルに確定済み。** `npm run build`（`vite build` + `scripts/postbuild.js`）で生成する `dist/Planner_ccmp_support.html` をリポジトリにコミットし配布物とする（開発ガイド.md「配布物（dist/）」参照）。ローカル Web サーバー同梱や PWA 化は、導入手順が増えるため採用しなかった。

**ビルド成果物のファイル名は `Planner_ccmp_support.html` に固定する。** Vite の入力ファイル（`index.html`、dev サーバーの既定エントリ）自体はリネームせず、`scripts/postbuild.js` が CSP ハッシュ埋め込みと同じタイミングでビルド後の `dist/index.html` を `dist/Planner_ccmp_support.html` にリネームする（`renameSync`）。

## 2. 技術構成

| 領域 | 採用技術 | 備考 |
| --- | --- | --- |
| 言語 | TypeScript（`strict` 有効） | 型でグラフ構造の不整合を早期に検出できる |
| ビルド | Vite + `vite-plugin-singlefile` | 単一 HTML への inline 化を自動化 |
| UI | フレームワークなし（素の DOM 操作） | 画面数が 1 のため大規模な UI ライブラリは不要。DOM 書き込みは `security/dom.ts` を唯一の窓口とする（7 章参照） |
| CSV パース | PapaParse をバンドル | 引用符内の改行・エスケープの正確な処理が要件。自前実装案も検討したが、実行時依存0件・専用ブラウザビルド同梱・当該要件に対する実績の豊富さから採用。MITライセンス（本プロジェクトと同一）。ビルド時バンドルのため実行時ネットワーク通信は発生しない |
| 図の描画 | SVG の直接生成 | 印刷・拡大に強い。Canvas はテキストの可読性で劣る |
| レイアウト計算 | 自前実装 | 汎用グラフレイアウトライブラリは AOA の制約（左→右、イベント番号順）と相性が悪い |
| 日付処理 | 標準の `Date`（UTC 基準） | 営業日計算のみのため標準 API で足りる |

すべての依存ライブラリはビルド時にバンドルする。実行時に外部リソースを参照しない。

## 4. データ構造（案）

機能仕様書 4.2.2 で定義した入出力の実体。

```
Task     = { id, name, assignees[], duration }
Edge     = { from: TaskId, to: TaskId }
Event    = { id, number, earliest, latest }
Arrow    = { from: EventId, to: EventId, kind: 'activity' | 'dummy', taskId?, duration }
Project  = { key, name, tasks: Task[], edges: Edge[], events: Event[], arrows: Arrow[], isolatedTasks: Task[] }
```

`TaskId` はプロジェクト内でのみ一意（機能仕様書 3.5.1）。プロジェクトをまたいで参照する場合は `ProjectKey + TaskId` の組を用いる。

手動編集（10 章）で用いる構造（案）：

```
EditSession = { fileName, edges: Edge[], undo: EditOp[], redo: EditOp[] }
EditOp      = { kind: 'add' | 'remove', from: TaskId, to: TaskId }
```

## 5. アローダイアグラム変換アルゴリズム

機能仕様書 4.2.1 の作図ルールをすべて満たすことを制約として、AON（タスクと依存関係）を AOA（イベントと矢線）へ変換する手順。

**手順 1：前処理**

- トポロジカルソートを試み、循環がある場合は変換を中止しエラーとする（機能仕様書 5 章）
- 自己参照辺を除去し警告とする

**手順 2：終了イベントの生成**

各タスク `t` に対し、その完了を表すイベント `e(t)` を 1 つ生成する。

**手順 3：開始イベントの決定**

タスク `t` の先行タスク集合を `pred(t)` とする。

| 条件 | 処理 |
| --- | --- |
| `pred(t) = ∅` | プロジェクト開始イベント `N₀` を開始イベントとする |
| `\|pred(t)\| = 1`（先行が `p`） | `e(p)` を開始イベントとする |
| `\|pred(t)\| ≥ 2` | `pred(t)` のタスク ID をソートした文字列をキーとして合流イベント `m` を生成（同一キーなら共有）。各 `p ∈ pred(t)` について `e(p) → m` のダミー矢線を張り、`m` を開始イベントとする |

同一の `pred(t)` を持つ複数タスクは、同じ開始イベントを共有する。

**手順 4：終端の接続**

後続タスクを持たないタスク `t` の `e(t)` から、プロジェクト終了イベント `Nz` へダミー矢線を張る。`e(t)` が 1 つしかない場合は `e(t)` を `Nz` とみなして縮約してよい。

**手順 5：ダミー矢線の削減**

以下の条件でダミーを縮約する。冗長なダミーは図の可読性を著しく損なうため、最低限この 2 つは実装する。

1. 合流イベント `m` の入辺がダミー 1 本のみである場合、そのダミーを縮約し `m` を上流イベントに統合する
2. イベント `e(p)` の出辺がダミー 1 本のみ、かつ そのダミーの先 `m` の入辺も 1 本のみである場合、両イベントを統合する

> **意図的な制限（既知の限界）：** ダミー本数の最小化は一般に NP 困難であるため、完全な最適化は行わない方針で確定している。上記の局所的な縮約（`reduceDummyArrows`）のみを実装し、最小性は保証しない。

**手順 6：並行作業の分離**

同一のイベント対 `(i, j)` を結ぶ実作業が 2 本以上ある場合、2 本目以降について新規イベント `k` を挿入し、`i → k`（実作業）＋ `k → j`（ダミー）に分解する（作図ルール 4 の遵守）。

**手順 6a：複数担当タスクの分割**（機能仕様書 3.6 参照）

タスク `t` に担当者が複数（`assignees.length ≥ 2`）いる場合、手順 2 で生成する `e(t)` の前段に、担当者ごとの実作業エッジを持たせる。

1. 元のタスク `t` の開始イベントから、担当者の人数分の実作業エッジ（各 `duration` は `t` と同一）を生成する。各エッジの終点として新規イベントを 1 つずつ追加する
2. 追加した各イベントから、`e(t)` へ 0 営業日のダミー矢線を張り、元のイベントに再合流させる
3. 各エッジは担当者ごとに色分けされる（機能仕様書 4.2.4）。リソース競合判定はこの分割後のエッジを単位として行う

これにより手順 6 の並行作業分離と同様、同一イベント対を結ぶ実作業が 1 本のみという作図ルールを満たす。

**手順 7：イベント番号付け**

トポロジカル順に 0 から連番を付与する。これにより全矢線 `(i, j)` について `i < j` が保証される。**同順位のイベントの順序は、イベント ID 文字列順に確定した**（`src/aoa/buildAoa.ts` の `numberEvents`。二分探索によるソート済み配列への挿入で決定的な順序を維持する）。

## 6. レイアウトアルゴリズム

`layout/layoutWorkspace.ts` は「営業日数単位の X」「行番号単位の Y」という抽象座標のみを算出し、実ピクセルへの変換・ズーム倍率の適用は `render/` 側の責務とする。

| 項目 | 仕様 |
| --- | --- |
| X 座標（抽象） | 機能仕様書 4.1.5 で定義した**グローバル営業日番号**（プロジェクト内相対 ES に、プロジェクトのオフセットを加えた値）に比例させる。`layout/` は常にこの営業日番号を出力し、軸モードでも変えない |
| X 座標（ピクセル変換） | **既定はカレンダー軸モード**（`ui/App` の `axisMode` 初期値 `"calendar"`。原点未定＝W315 のときのみ営業日軸へフォールバック）。営業日軸では `DEFAULT_DIAGRAM_CONFIG.pixelsPerDay`（**24px/営業日**）で変換し、目盛りラベルは**最終タスク終了（`lastDay = Math.ceil(maxX)`）を 0 とした残営業日数** `String(lastDay - day)`（表示のみ、`toPixelX` は不変）。**カレンダー軸モード**（`renderDiagram` の第5引数 `calendarAxisInput` に共通時間軸の原点日付と非営業日カレンダーを渡す）では、`render/calendarAxis.ts` の `buildCalendarAxis` がグローバル営業日番号を「原点起点の実カレンダー日インデックス」へ写像し、`DEFAULT_DIAGRAM_CONFIG.pixelsPerCalendarDay`（**18px/暦日**）で変換する。土日祝は目盛りが飛び、隙間に薄い網掛け（`<rect>`）を敷く。グリッド線は営業日ごと、日付ラベルは週初の営業日のみ（`M/D` ／ 月替わり `M月D日` ／ 年替わり `YYYY年M月D日`）。営業日番号→実日付の逆変換は `calendar/businessDays.ts` の `addBusinessDays`。原点日付は `workspace/timeline.ts` の `computeTimeline().originDate` を `Workspace` が保持し、`getTimeAxisOrigin()` / `getHolidayKeys()` で公開する。原点が定まらない（W315）ときは切り替え不可 |
| 横軸の目盛り行（軸SVG） | `renderDiagram` は `{ diagram, axis }`（`RenderedDiagram`）を返す。`axis` は高さ `config.axisHeight` の別 SVG で、目盛りラベル・短いティック・下端の水平線・（カレンダー時）上端ぶんの非営業日網掛けを持つ。`ui/App` は固定クリップ枠 `.diagram-axis-layer`（変形しない）の内側の `.diagram-axis-inner` に載せ、`applyTransform` が `.diagram-axis-inner` に `translate(translateX, 0) scale(scale)`（縦は固定）を、`.diagram-axis-layer` に `height = axisHeight * scale` を適用する（枠自体を変形すると `overflow:hidden` のクリップごと画面外へ出て軸が消える）。営業日軸のラベルは日ごとに描かれるため、`App.thinAxisLabels()` が拡大率に応じて `<text>` の `display` を切り替えて間引く（画面ピッチ `pixelsPerDay*scale` が `AXIS_LABEL_MIN_GAP_PX(34)` を下回ると末尾＝`"0"` を残して stride ごとに間引く。カレンダー軸は既に週次で疎なので対象外）。`diagram`（本体）は縦グリッド線（全高）・網掛け（全高）・矢線・ノード・境界線・プロジェクト名を持つ |
| レーン（行）割り当ての不変条件 | `layout/layoutWorkspace.ts` の行割り当ては、グラフ位相＋`event.number`＋決定的タイブレーク（`arrow.durationBusinessDays` / `arrow.assignee`）と、**アロー衝突回避のためのプロジェクト内相対 ES**（`x = es + offset` の `es`）のみに依存する。ES は軸モードに依存しない値なので、`renderDiagram` に `calendarAxisInput` を渡しても `WorkspaceLayout` の `row` は不変。**軸モード（カレンダー/営業日）でレーン並びが変わってはならない（カレンダー表示を正とする）。** カレンダー日付・`pixelsPerDay`・`calendarAxisInput` はレイアウトに渡さない。今後の変更でもこの不変条件を守る |
| アローの衝突回避配置（修正3） | 分岐を空き行へ詰める際、バンド矩形（行×層）の非重複だけでなく、**実際に水平に描かれるアロー区間**が別タスクの区間と同一行・X厳密重複しない行を選ぶ。判定対象は分岐内アロー＋backbone へ繋ぐ接続ダミー（`branchSegments` / `horizontalRun` は `render/renderDiagram.ts` の `elbowPoints` を写したもの。`RUN_DAYS = DIAGONAL_RUN/pixelsPerDay = 1`）。空きが無ければ従来どおり最外へ |
| ダミー×実作業の重なり解消（修正2） | 上記の後、行割り当て全体を走査し、ダミー矢線と別タスクの実作業矢線が同一行で重なる箇所を「後続タスクを1つ下のレーンへ」で解消する（`bumpCollidingArrows`）。実作業の終点イベント（backbone でない）と、その終点と同じ行にある下流イベントの部分木を +1 する。行は単調増加なので有限回で停止（安全弁 `MAX_ITER`）。実データ（planA）で 23 → 5 に減少。残る 5 はいずれも row0（backbone）を走る接続ダミーで、row0 は固定のため押し出し不能（既知の限界） |
| 合流イベントの最上位レーン揃え（修正4） | 入辺が2本以上かつ全て `kind:"dummy"`、出辺が1本以上、backbone でないイベント（＝`startEventOf` の `merge:` に相当）は、行割り当ての最後に `min(入辺ダミーの先行イベントの行)` へ揃える（`realignMergeEvents`）。下流イベントの行は据え置き（`merge→end:task` の斜め線がタスクに重なるのは許容） |
| Y 座標 | **代表クリティカルパス（`Project.criticalPaths[0]`、backbone）を行0に固定して一直線に配置する**（`criticalBackboneEventIds`）。同着のクリティカルパスが複数存在する場合（機能仕様書 4.1.3）も先頭の1本のみを揃え、それ以外は通常のバリセンター法で扱う。**backbone以外のイベントは、backboneを経由しない矢線でつながった連結成分＝「分岐」ごとに1つの行帯を専有する**（`groupNonBackboneBranches`）。ダミー矢線のみで構成される分岐も同様に1行帯を専有する。分岐が占める層の範囲（分離してから合流するまでの長さの近似）が短いものから順に、backboneに最も近い空き行へ詰める（`findInnerRowStart`）。**層の範囲が重ならない分岐同士は同じ行を共有し**、重なる場合のみ外側へ新しい帯を追加する（`layoutProjectRows`）。各分岐内部は、まず**最長パス（経路上のタスク数＝辺数が最多の1本。同数は所要日数合計→イベント番号で決定）をローカル行0に固定**し（`longestPathEventIds`。project 単位の `selectBackbonePath` の分岐版）、残りのイベントを、依存関係の到達可能性（最長経路長）による層分けと隣接層の平均位置（バリセンター）に基づく前進・後進4パスの並べ替えで周囲に配置する（`computeRowsForSubgraph` / `assignRowsByOrder`）。これにより分岐した複数タスクの鎖が行をまたいで折れ曲がらない。層内の行間隔は `render/renderDiagram.ts` の `DEFAULT_DIAGRAM_CONFIG.rowHeight`（**84px に確定**） |
| タスク名ラベル | 実作業の矢線（`kind: "activity"`）には、矢線の上（Y座標が小さい側にオフセット）にタスク名をテキストで表示する（`render/renderDiagram.ts` の `renderDiagram` 内、`DEFAULT_DIAGRAM_CONFIG.labelFontSize` で文字サイズを指定）。ダミー矢線（`kind: "dummy"`、タスクIDを持たない）には表示しない |
| プロジェクト名ラベル | 各プロジェクト帯の先頭（最小 X・最小行）の上部に、プロジェクト名テキスト用の行高を確保する（機能仕様書 3.5.4、UI・UX仕様書 4.2.4）。左詰め。孤立タスクの独立プロジェクトには置かない |

## 7. セキュリティ実装

機能仕様書 6 章の防御層を実現する具体的な関数・処理。CSV に由来する文字列（タスク名・ファイル名・タスク ID 等）を画面に表示するすべての箇所で、以下を適用する。

### 7.1 DOM API の使用ルール

CSV に由来する文字列（タスク名、ファイル名、タスク ID、エラーメッセージ中の該当箇所等）を DOM／SVG へ反映する際のルールを以下に定める（機能仕様書 6.2 参照）。

| 用途 | 扱い |
| --- | --- |
| テキストの設定 | CSV 由来の文字列は `Node.textContent` **のみ**で設定する。単一のテキストノードとして扱われ、HTML／SVG タグとして解釈されない |
| 属性の設定 | `Element.setAttribute` は使用するが、**CSV 由来の文字列を渡してよい対象は限定する。** `href`／`xlink:href`／`style`／`on*` 系のイベント属性の値、および属性名・要素名そのものには CSV 由来の文字列を使用しない。属性値として使用してよいのは、数値座標・配色パレットが生成した色・固定の列挙値など、**アプリ自身が生成した値に限る** |
| 要素の生成 | `document.createElement` / `document.createElementNS`。SVG 要素は名前空間付きの `createElementNS` を用いる（機能仕様書 4.2.2 参照） |

**禁止 API：** `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write` / `document.writeln`。CSV に由来する文字列をこれらに渡してはならない。

`textContent` は内容にかかわらず HTML／SVG として解釈されないため、テキスト表示では手動のエスケープ関数を主たる防御としない。ただし属性は上記の制限が必要で、`setAttribute` を使うだけでは安全とは限らない。

### 7.2 リンク化の禁止

CSV 由来の文字列は `<a>` 要素を生成せず、URL らしき文字列であっても常にテキストノード（7.1）として表示する。この方針により、URL のスキーム検証や `rel="noopener noreferrer"` の付与といった、リンク生成に付随する防御は不要になる。

### 7.3 CSP

`<meta http-equiv="Content-Security-Policy" content="...">` により指定する。ディレクティブ全文と各項目の根拠は機能仕様書 6.3 を参照。

`script-src` を `'unsafe-inline'` ではなくビルド後の実際のインラインスクリプトの SHA-256 ハッシュ値による許可とすることで、たとえ 7.1 の DOM API 使用ルールが回避され注入が発生しても、正規のスクリプト以外は実行されない。ただし `'unsafe-inline'`（および `'unsafe-hashes'`）を外すと `onclick` 等のインライン属性も CSP でブロックされるため、`addEventListener` によるイベント登録（機能仕様書 6.2）は抜け道封じというより**この CSP のもとで動作させるための前提**となる。

ビルドプロセスには以下の手順が必要となる。

1. 単一 HTML への inline 化（本書 1 章）が完了した時点の `<script>` の内容に対して SHA-256 ハッシュ値を算出する
2. 算出したハッシュ値を、同じ HTML 内の CSP `<meta>` タグの `script-src` に埋め込む
3. CSP `<meta>` タグを `<head>` の先頭付近、かつ許可対象の `<script>` より前に出力する（機能仕様書 6.3 参照）。ビルド後の HTML でこの順序を検証するステップを設ける
4. バンドルする依存ライブラリ（PapaParse）のライセンス表記をフッターに含める（機能仕様書 7.3 参照）。依存が PapaParse 1件のみのため、ビルド時の自動収集ではなく `src/ui/App.ts` 内の静的な文字列（`PapaParse (MIT License)`）とした。依存ライブラリが増える場合はこの表示が実態と乖離しないよう都度見直すこと（開発ガイド.md「技術構成」参照）

**上記 1〜3 は `npm run build` の一部として `scripts/postbuild.js` に実装済み（専用のビルドステップとして `vite build` の後に実行する。同スクリプトは配布物ファイル名のリネームも兼ねる。本章「配布形態」参照）。**

### 7.4 手動編集ペインの DOM 生成

依存関係の手動編集ペイン（機能仕様書 4.3）のコンテキストメニュー・表・「変更内容を出力」のダウンロード導線も、他の描画と同様に `security/dom.ts` を唯一の窓口として生成する（`innerHTML` 等は使わない）。ネイティブの `contextmenu` は `preventDefault` し、メニューは要素生成で組み立てる。ダウンロードは `data:text/csv;charset=utf-8,...` を `href` に持つ `<a download="後続タスク変更.csv">` で行い、CSV 文字列は PapaParse の `unparse`（`csv/` のラッパ経由）で生成する。Blob URL を用いる場合はセキュリティ仕様書 6.4 に従い破棄する。

## 10. 手動編集の実装

機能仕様書 4.3 を実現する構成。

### 10.1 パイプラインの分割

`workspace/pipeline.ts` の `processFile` を 2 段に分ける。

| 段 | 内容 |
| --- | --- |
| 前半 | CSV テキスト → `{ tasks, edges, warnings }`（ステージ [2]〜[5]）。読み込み時に 1 回だけ実行し、結果を `Workspace` が保持する |
| 後半 | `{ tasks, edges }` → AON グラフ・AOA・スケジュール・CCPM（ステージ [6]〜[12]）。読み込み時と、「グラフを更新」のたびに実行する |

手動編集が触るのは前半の出力である `edges`（`validate/` が後続タスクを解決した直後の集合。定期的タスク宛ての辺もこの層では保持される）。後半の `buildGraph` が定期的タスク除外・孤立分離を毎回やり直すため、編集結果はそのまま後半へ渡せる。

### 10.2 `Workspace` の追加 API

- 読み込み済みファイルごとに前半の出力（`tasks`・`edges`）を保持する。
- `applyManualEdits(fileName, edges)`： 与えられた `edges` で後半を再実行して当該プロジェクトを差し替え、あわせて共通時間軸（機能仕様書 4.1.5）を再計算する。
- 警告は **append しない**。`allWarnings` から当該 `fileName` 由来のものを除き、再実行で得た警告を入れ直す（`setHolidayKeys` の全消し→再構築と同じ考え方）。

### 10.3 編集操作（`edit/`）

- 辺の追加・削除は `edges` 上の純粋操作。
- 循環チェックは**追加時のみ**、対象プロジェクトの `edges` ＋ 追加辺に対して行う（`graph/buildGraph.ts` の `topologicalSort` を再利用）。削除では不要。
- 変更タスクの差分： 読み込み時の `edges`（前半の出力）と現在の `edges` を突き合わせ、後続 ID 集合が変わったタスクを列挙する。変更マーク・「変更内容を出力」の対象・同ボタンの活性は、いずれもこの結果で決まる。
- 出力 CSV 文字列も `edit/` で生成する（`csv/` のラッパ経由で PapaParse の `unparse`）。

### 10.4 元に戻す／やり直し

- プロジェクト（`fileName`）ごとに `undo`／`redo` スタックを持つ。
- どちらも全履歴を保持する。新規の編集操作で `redo` を空にする。
- 実行はペイン上部のボタンのみ（キーボードショートカットは設けない）。
